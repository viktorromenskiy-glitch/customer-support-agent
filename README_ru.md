# Интеллектуальный агент техподдержки — RAG + классификация + MLOps

*[English version available here](README.md) · [Українська версія тут](README_uk.md)*

**Инструмент пакетной сортировки CSV (категория, приоритет, пометка «передать человеку»): см. [README_triage.md](README_triage.md) (на английском).** Таблица результатов ниже относится к прежнему RAG-конвейеру: она показывает согласие с метками языковой модели, а не точность относительно решений людей.

Полноценная система автоматизации техподдержки, построенная на реальных, публичных данных Twitter (Apple, Amazon, Uber, Spotify, Delta — 20 000 реальных обращений в поддержку). При поступлении нового тикета система классифицирует его, находит семантически похожие прошлые решения, и принимает решение — сгенерировать автоматический черновик ответа, обоснованный реальным прецедентом, или эскалировать человеку.

Это портфолио-проект. Он демонстрирует полный жизненный цикл: получение и очистку реальных (не синтетических) данных, честный эмпирический выбор модели, работающий RAG-конвейер, и явно задокументированный набор реальных ограничений — вместо отполированного, но вводящего в заблуждение демо.

## Архитектура

```
Новый тикет
    │
    ▼
Единый эмбеддинг (Voyage AI voyage-4-lite)
    │
    ├──────────────┬─────────────────┐
    ▼              ▼                 ▼
Классификатор   Классификатор    Семантический
категории       приоритета       поиск (топ-5
(8 классов)     (4 уровня)       похожих тикетов)
    │              │                 │
    └──────────────┴─────────────────┘
                   │
                   ▼
        Правило решения агента:
   порог сходства зависит от
   приоритета -> черновик или эскалация
                   │
        ┌──────────┴──────────┐
        ▼                     ▼
  Черновик ответа        Эскалация человеку
  (Claude, обоснован
  найденными случаями)
```

Один вызов эмбеддинга на тикет обслуживает все три последующие задачи (классификация x2, поиск) — а не три отдельных вызова.

## Результаты — честно

| Задача | Метрика | TF-IDF (baseline) | Эмбеддинги (финал) |
|---|---|---|---|
| Категория (8 классов) | Accuracy | 58.95% | **70.57%** |
| Категория (8 классов) | F1 macro | 0.567 | **0.686** |
| Приоритет (4 уровня) | Accuracy | 50.10% | **60.40%** |
| Приоритет (4 уровня) | F1 macro | 0.482 | **0.594** |
| Семантический поиск | Совпадение категории в топ-5 | 36.3% (TF-IDF) | **58.1%** |

Все метрики оценены на **временном** разбиении train/test (самые ранние 80% тикетов — обучение/база знаний, самые поздние 20% — отложенный тест), а не на случайном — чтобы избежать оценки модели на данных, «подглядывающих из будущего», и чтобы отразить реальный сценарий использования (поиск среди уже решённых тикетов для помощи с новым). Тест — последние 4000 тикетов, они охватывают 12 календарных дней (с 22 ноября по 3 декабря 2017). Как модели поведут себя в другие периоды и у других компаний, не проверялось.

Метки категории и приоритета получены через LLM (Claude Haiku), а не размечены вручную — у исходного датасета нет готовых меток ни для того, ни для другого. Это форма weak supervision / дистилляции: LLM размечает весь датасет один раз, а дешёвый и быстрый классический классификатор (логистическая регрессия) обучается на этих метках для использования в реальном времени — вместо вызова LLM на каждый входящий тикет только ради классификации. Поэтому все значения точности показывают, насколько классификатор согласен с метками LLM, а не как часто он совпадает с решением человека. Отдельная проверка на 200 вручную размеченных тикетах выполнена позже, только для инструмента CSV-сортировки (два разметчика): см. раздел «Check on 200 tickets» в [README_triage.md](README_triage.md) (на английском). Цифр этой таблицы она не касается.

### Независимая перепроверка (16.10.2026)

Все числа из таблицы выше пересчитаны заново по сохранённым эмбеддингам и меткам. Они совпали, кроме пунктов ниже.

- **TF-IDF, приоритет:** при пересчёте получается 50.10% (F1 0.482), а не 50.28% (0.484), как было написано раньше. Скрипт, по которому считалось исходное значение, найти не удалось.
- **Поиск:** на всех 4000 тестовых тикетах категория совпадает в топ-5 в 58.6% случаев (95% ДИ 57.5–59.7%) — на сохранённых эмбеддингах типа document. Значение 58.1% выше получено на выборке из 500 тикетов с эмбеддингами типа query, а их не сохранили. Для сравнения: случайный поиск даёт 14.7% (с учётом реальных долей категорий; 12.5% было бы верно, только если бы все 8 категорий встречались одинаково часто), а если всегда брать соседей из самой частой категории — 19.8%.
- **Дубликаты:** у 55 из 4000 тестовых тикетов (1.4%) в обучающей выборке есть точная копия, если убрать @упоминания и ссылки и не учитывать регистр и пробелы. Без них точность по категориям падает примерно на 0.3 п.п. Дубликаты, переписанные другими словами, не искали.
- **Точность по категориям:** 95% ДИ 69.1–71.9%. Эмбеддинги лучше TF-IDF на 10.1–13.1 п.п. (парный тест, p < 1e-50).
- **Убран признак:** раньше модели получали флаг `is_dm_escalation`, который считался по ответу компании, а у агента этого ответа при поступлении нового тикета нет. Признак убрали. Результаты на отложенной части те же: категория 70.60% (F1 0.686), приоритет 60.42% (F1 0.594).

## Почему эмбеддинги, а не TF-IDF

TF-IDF («мешок слов») находит совпадения по общей **лексике**, независимо от смысла. Конкретный, реальный случай сбоя, обнаруженный в процессе разработки: тикет о неисправных ячейках выдачи Amazon нашёл как «наиболее похожий» совершенно не связанный твит про номер версии iOS — единственное, что их объединяло, — случайно совпавшая фраза «I've got». Семантические эмбеддинги исправили именно этот случай, и агрегатная метрика качества поиска (совпадение категории в топ-5) выросла с 36.3% до 58.1%. Оба классификатора затем были пересобраны на тех же эмбеддингах, поскольку та же проблема представления данных, вероятно, затрагивала и их — что метрики выше и подтвердили.

## Известные ограничения (задокументированы, а не скрыты)

- **Короткие, резкие, негативные сообщения остаются слабым местом.** `"@Delta That's not good enough."` был неверно классифицирован TF-IDF-версией (как положительный отзыв, низкий приоритет), и хотя версия на эмбеддингах исправила именно этот пример, сарказм и сухое занижение в целом не улавливаются надёжно ни тем, ни другим подходом — оба опираются только на текст, без истории переписки или моделирования тона.
- **F1 macro приоритета (0.594) заметно ниже, чем у категории (0.686).** Срочность — более размытый, тональный сигнал, чем тема, и его по своей природе сложнее прочитать по одному короткому сообщению.
- **Категория «сбой сервиса» и приоритет «критический» — самые сложные классы** — оба являются миноритарными в обучающих данных, и оба пересекаются по лексике с соседними категориями (жалоба на задержку рейса звучит очень похоже на обычную жалобу на качество).
- **Пороги эскалации подобраны по осмотру примеров, а не через систематический поиск порога** (например, оптимизацию по ROC-кривой) — разумный следующий шаг, ещё не сделанный.
- **Лимиты запросов:** бесплатный уровень Voyage AI по умолчанию даёт 3 запроса в минуту, пока к аккаунту не добавлена карта (200 млн бесплатных токенов при этом остаются бесплатными в любом случае) — предоставленные скрипты включают логику повторных попыток для работы в этих условиях, но без привязанной карты весь конвейер займёт заметно больше времени.

## Структура репозитория

```
data_pipeline/
  prepare_dataset.py           # Фильтрация исходного CSV Twitter по компаниям, восстановление пар запрос/ответ
  sample_and_filter.py         # Фильтрация по длине/DM-эскалации, стратифицированная выборка до управляемого размера
  label_categories.py          # LLM-разметка (Claude) категории тикета, пакетами
  label_priority.py            # LLM-разметка (Claude) приоритета тикета, пакетами
training/
  build_semantic_rag.py        # Эмбеддинг базы знаний + оценка качества поиска (Voyage AI)
  train_final_embedding_classifiers.py  # Обучение финальных классификаторов категории и приоритета на эмбеддингах
agent.py                       # Основной оркестратор: эмбеддинг -> классификация -> поиск -> решение -> ответ/эскалация
app.py                         # Обёртка FastAPI с эндпоинтом /handle_ticket
Dockerfile
requirements.txt
```

## Запуск

### 1. Конвейер данных (воспроизводит датасет с нуля)

Требует исходный датасет [Customer Support on Twitter](https://www.kaggle.com/datasets/thoughtvector/customer-support-on-twitter) с Kaggle (`twcs.csv`).

```bash
python data_pipeline/prepare_dataset.py
python data_pipeline/sample_and_filter.py
```

### 2. Разметка (нужен ключ Anthropic API — стоимость: несколько долларов суммарно)

```bash
export ANTHROPIC_API_KEY="sk-ant-..."
python data_pipeline/label_categories.py
python data_pipeline/label_priority.py
```

### 3. Построение семантического индекса и обучение классификаторов (нужен ключ Voyage AI — бесплатного уровня хватает с большим запасом)

```bash
export VOYAGE_API_KEY="..."
python training/build_semantic_rag.py
python training/train_final_embedding_classifiers.py
```

### 4. Запуск API локально

```bash
export VOYAGE_API_KEY="..."
export ANTHROPIC_API_KEY="..."
uvicorn app:app --reload
```

Затем: `POST http://localhost:8000/handle_ticket` с `{"text": "...", "company": "AmazonHelp"}`.

### 5. Или запуск в Docker

```bash
docker build -t customer-support-agent .
docker run -e VOYAGE_API_KEY=... -e ANTHROPIC_API_KEY=... -p 8000:8000 customer-support-agent
```

Артефакты моделей (`.joblib`, `.npy`, `kb_with_index.csv`) не хранятся в git (см. `.gitignore`) из-за размера — сгенерируйте их через конвейер выше, либо используйте Git LFS, если хотите закоммитить их напрямую.
