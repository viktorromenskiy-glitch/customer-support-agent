# Інтелектуальний агент техпідтримки — RAG + класифікація + MLOps

*[English version available here](README.md) · [Русская версия здесь](README_ru.md)*

**Інструмент пакетного сортування CSV (категорія, пріоритет, позначка «передати людині»): див. [README_triage.md](README_triage.md) (англійською).** Таблиця результатів нижче стосується попереднього RAG-конвеєра: вона показує узгодженість з мітками мовної моделі, а не точність щодо рішень людей.

Повноцінна система автоматизації техпідтримки, побудована на реальних, публічних даних Twitter (Apple, Amazon, Uber, Spotify, Delta — 20 000 реальних звернень у підтримку). При надходженні нового тікета система класифікує його, знаходить семантично схожі минулі рішення, і приймає рішення — згенерувати автоматичний чернетковий варіант відповіді, обґрунтований реальним прецедентом, або ескалювати людині.

Це портфоліо-проєкт. Він демонструє повний життєвий цикл: отримання та очищення реальних (не синтетичних) даних, чесний емпіричний вибір моделі, працюючий RAG-конвеєр, і явно задокументований набір реальних обмежень — замість відполірованого, але оманливого демо.

## Архітектура

```
Новий тікет
    │
    ▼
Єдиний ембеддинг (Voyage AI voyage-4-lite)
    │
    ├──────────────┬─────────────────┐
    ▼              ▼                 ▼
Класифікатор    Класифікатор     Семантичний
категорії       пріоритету       пошук (топ-5
(8 класів)      (4 рівні)        схожих тікетів)
    │              │                 │
    └──────────────┴─────────────────┘
                   │
                   ▼
        Правило рішення агента:
   поріг схожості залежить від
   пріоритету -> чернетка або ескалація
                   │
        ┌──────────┴──────────┐
        ▼                     ▼
  Чернетка відповіді     Ескалація людині
  (Claude, обґрунтована
  знайденими випадками)
```

Один виклик ембеддингу на тікет обслуговує всі три подальші завдання (класифікація x2, пошук) — а не три окремі виклики.

## Результати — чесно

| Завдання | Метрика | TF-IDF (baseline) | Ембеддинги (фінал) |
|---|---|---|---|
| Категорія (8 класів) | Accuracy | 58.95% | **70.57%** |
| Категорія (8 класів) | F1 macro | 0.567 | **0.686** |
| Пріоритет (4 рівні) | Accuracy | 50.10% | **60.40%** |
| Пріоритет (4 рівні) | F1 macro | 0.482 | **0.594** |
| Семантичний пошук | Збіг категорії в топ-5 | 36.3% (TF-IDF) | **58.1%** |

Усі метрики оцінені на **часовому** розбитті train/test (найраніші 80% тікетів — навчання/база знань, найпізніші 20% — відкладений тест), а не на випадковому — щоб уникнути оцінки моделі на даних, які «підглядають з майбутнього», і щоб відобразити реальний сценарій використання (пошук серед уже вирішених тікетів для допомоги з новим). Тест — останні 4000 тікетів, вони охоплюють 12 календарних днів (з 22 листопада по 3 грудня 2017). Як моделі поводитимуться в інші періоди та в інших компаній, не перевірялося.

Мітки категорії та пріоритету отримані через LLM (Claude Haiku), а не розмічені вручну — у вихідного датасету немає готових міток ні для того, ні для іншого. Це форма weak supervision / дистиляції: LLM розмічає весь датасет один раз, а дешевий і швидкий класичний класифікатор (логістична регресія) навчається на цих мітках для використання в реальному часі — замість виклику LLM на кожен вхідний тікет лише заради класифікації. Тому всі значення точності показують, наскільки класифікатор погоджується з мітками LLM, а не як часто він збігається з рішенням людини. Окрема перевірка на 200 вручну розмічених тікетах виконана пізніше, лише для інструмента CSV-сортування (двоє розмітників): див. розділ «Check on 200 tickets» у [README_triage.md](README_triage.md) (англійською). Цифр цієї таблиці вона не стосується.

### Незалежна перевірка (16.10.2026)

Усі числа з таблиці вище перераховано заново за збереженими ембедингами та мітками. Вони збіглися, окрім пунктів нижче.

- **TF-IDF, пріоритет:** при перерахунку виходить 50.10% (F1 0.482), а не 50.28% (0.484), як було написано раніше. Скрипт, за яким рахувалося початкове значення, знайти не вдалося.
- **Пошук:** на всіх 4000 тестових тікетах категорія збігається в топ-5 у 58.6% випадків (95% ДІ 57.5–59.7%) — на збережених ембедингах типу document. Значення 58.1% вище отримано на вибірці з 500 тікетів з ембедингами типу query, а їх не зберегли. Для порівняння: випадковий пошук дає 14.7% (з урахуванням реальних часток категорій; 12.5% було б правильним, лише якби всі 8 категорій траплялися однаково часто), а якщо завжди брати сусідів із найчастішої категорії — 19.8%.
- **Дублікати:** у 55 із 4000 тестових тікетів (1.4%) у навчальній вибірці є точна копія, якщо прибрати @згадки та посилання й не зважати на регістр і пробіли. Без них точність за категоріями падає приблизно на 0.3 в.п. Дублікати, переписані іншими словами, не шукали.
- **Прибрано ознаку:** раніше моделі отримували прапорець `is_dm_escalation`, який рахувався за відповіддю компанії, а в агента цієї відповіді під час надходження нового тікета немає. Ознаку прибрали. Результати на відкладеній частині ті самі: категорія 70.60% (F1 0.686), пріоритет 60.42% (F1 0.594).

## Чому ембеддинги, а не TF-IDF

TF-IDF («мішок слів») знаходить збіги за спільною **лексикою**, незалежно від сенсу. Конкретний, реальний випадок збою, виявлений у процесі розробки: тікет про несправні комірки видачі Amazon знайшов як «найбільш схожий» абсолютно не пов'язаний твіт про номер версії iOS — єдине, що їх об'єднувало, — випадково співпала фраза «I've got». Семантичні ембеддинги виправили саме цей випадок, і агрегатна метрика якості пошуку (збіг категорії в топ-5) зросла з 36.3% до 58.1%. Обидва класифікатори потім були перезібрані на тих самих ембеддингах, оскільки та сама проблема представлення даних, ймовірно, стосувалася і їх — що метрики вище і підтвердили.

## Відомі обмеження (задокументовані, а не приховані)

- **Короткі, різкі, негативні повідомлення залишаються слабким місцем.** `"@Delta That's not good enough."` був невірно класифікований TF-IDF-версією (як позитивний відгук, низький пріоритет), і хоча версія на ембеддингах виправила саме цей приклад, сарказм і сухе применшення загалом не вловлюються надійно жодним з двох підходів — обидва спираються лише на текст, без історії листування чи моделювання тону.
- **F1 macro пріоритету (0.594) помітно нижчий, ніж у категорії (0.686).** Терміновість — більш розмитий, тональний сигнал, ніж тема, і його за своєю природою складніше прочитати за одним коротким повідомленням.
- **Категорія «збій сервісу» та пріоритет «критичний» — найскладніші класи** — обидва є міноритарними в навчальних даних, і обидва перетинаються за лексикою з сусідніми категоріями (скарга на затримку рейсу звучить дуже схоже на звичайну скаргу на якість).
- **Пороги ескалації підібрані шляхом огляду прикладів, а не через систематичний пошук порогу** (наприклад, оптимізацію за ROC-кривою) — розумний наступний крок, ще не зроблений.
- **Ліміти запитів:** безкоштовний рівень Voyage AI за замовчуванням дає 3 запити на хвилину, поки до акаунту не додано картку (200 млн безкоштовних токенів при цьому залишаються безкоштовними в будь-якому випадку) — надані скрипти включають логіку повторних спроб для роботи в цих умовах, але без прив'язаної картки весь конвеєр займе помітно більше часу.

## Структура репозиторію

```
data_pipeline/
  prepare_dataset.py           # Фільтрація вихідного CSV Twitter за компаніями, відновлення пар запит/відповідь
  sample_and_filter.py         # Фільтрація за довжиною/DM-ескалацією, стратифікована вибірка до керованого розміру
  label_categories.py          # LLM-розмітка (Claude) категорії тікета, пакетами
  label_priority.py            # LLM-розмітка (Claude) пріоритету тікета, пакетами
training/
  build_semantic_rag.py        # Ембеддинг бази знань + оцінка якості пошуку (Voyage AI)
  train_final_embedding_classifiers.py  # Навчання фінальних класифікаторів категорії та пріоритету на ембеддингах
agent.py                       # Основний оркестратор: ембеддинг -> класифікація -> пошук -> рішення -> відповідь/ескалація
app.py                         # Обгортка FastAPI з ендпоінтом /handle_ticket
Dockerfile
requirements.txt
```

## Запуск

### 1. Конвеєр даних (відтворює датасет з нуля)

Потребує вихідний датасет [Customer Support on Twitter](https://www.kaggle.com/datasets/thoughtvector/customer-support-on-twitter) з Kaggle (`twcs.csv`).

```bash
python data_pipeline/prepare_dataset.py
python data_pipeline/sample_and_filter.py
```

### 2. Розмітка (потрібен ключ Anthropic API — вартість: кілька доларів сумарно)

```bash
export ANTHROPIC_API_KEY="sk-ant-..."
python data_pipeline/label_categories.py
python data_pipeline/label_priority.py
```

### 3. Побудова семантичного індексу та навчання класифікаторів (потрібен ключ Voyage AI — безкоштовного рівня вистачає з великим запасом)

```bash
export VOYAGE_API_KEY="..."
python training/build_semantic_rag.py
python training/train_final_embedding_classifiers.py
```

### 4. Запуск API локально

```bash
export VOYAGE_API_KEY="..."
export ANTHROPIC_API_KEY="..."
uvicorn app:app --reload
```

Потім: `POST http://localhost:8000/handle_ticket` з `{"text": "...", "company": "AmazonHelp"}`.

### 5. Або запуск у Docker

```bash
docker build -t customer-support-agent .
docker run -e VOYAGE_API_KEY=... -e ANTHROPIC_API_KEY=... -p 8000:8000 customer-support-agent
```

Артефакти моделей (`.joblib`, `.npy`, `kb_with_index.csv`) не зберігаються в git (див. `.gitignore`) через розмір — згенеруйте їх через конвеєр вище, або використовуйте Git LFS, якщо хочете закомітити їх напряму.
